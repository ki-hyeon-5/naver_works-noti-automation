# 01. 확정 비즈니스 요구사항 명세서 (Requirements Specification)

본 문서는 사용자와의 합의 및 최종 결정을 집대성한 기준 명세서입니다.

---

## 1. 시스템 환경 및 배포 요구사항
- **REQ-ENV-01:** 대상 OS는 Windows 11 64bit이며, 사내 PC 환경(Intel i9-12900, RAM 32GB, 백그라운드 모니터링 툴 다수 구동)에서 가볍고 빠르게 동작해야 한다.
- **REQ-ENV-02:** 사용자 PC에 Python, 외부 RDB 서버(MySQL, PostgreSQL 등)를 별도 설치하지 않고 포터블하게 실행되어야 한다.
- **REQ-ENV-03:** 배포 형식은 **PyInstaller onedir** 압축 폴더(`NotiAutomation/`) 형태로 제공하며, 실행 파일(`.exe`) 외부의 `data/` 및 `config/` 디렉터리에 데이터를 영속화하여 업데이트 시 데이터가 유실되지 않도록 한다.
- **REQ-ENV-04:** 로컬 처리(알람 파싱, 담당자 매칭, 중복 검사, 노티 문구 생성)는 20건 알람 및 매핑 데이터 각 1,000행 기준 **목표 1초 / 최대 5초 이내**에 완료되어야 한다.

---

## 2. 알람 입력 및 파싱 요구사항
- **REQ-PARSE-01 (입력 형태):** 관제 웹 테이블에서 마우스로 드래그 복사한 텍스트로, `Status :` 같은 항목 라벨 없이 순수 값(Value)만 들어오며 줄바꿈(Enter)과 탭이 불규칙하다.
- **REQ-PARSE-02 (필드 순서):** 알람 1건당 13개 필드 순서는 아래와 같다.
  `Status`, `Resolved`, `No Data`, `Start At`, `Duration`, `Target`, `Alert Name`, `Detail`, `Init Value`, `Last Value`, `Severity`, `Last Actor`, `FingerPrint`.
- **REQ-PARSE-03 (다중 알람 분리):** `Firing` 키워드와 `Start At` 일시 정규식(`YYYY-MM-DD HH:MM:SS`), `Duration` 정규식을 앵커로 삼아 다중 알람을 분리한다.
- **REQ-PARSE-04 (NoData 처리):** `No Data == "NoData"` 또는 `Alert Name == "DataSourceNoData"`인 비정상 알람은 **노티 검토 목록에 올리지 않고 Jira 등록 대상에서도 제외**한다. 단, 메인 화면 요약 알림(예: "총 5건 중 NoData 2건 제외됨") 및 로그에 제외 사유를 기록한다. `Detail`에 `$xxx`가 포함되어 있다는 이유만으로 NoData로 취급하지 않는다.
- **REQ-PARSE-05 (필수값 검증):**
  - `Target`이 `-`이거나 비어있으면 `[확인필요: 대상없음]`으로 표기.
  - `Start At` 날짜 형식이 올바르지 않으면 `[확인필요: 시간오류]`로 표기.
  - 확인필요 항목이 포함된 알람은 사용자가 화면에서 올바르게 수정하기 전까지 **Jira 등록을 차단**한다.
- **REQ-PARSE-06 (클러스터 추출):** `Detail` 시작 부분에 신뢰할 수 있는 `clusternamespace | 상세내용` 패턴이 존재할 경우에만 `|` 좌측 문자열을 추출해 노티 최상단 `클러스터 : {namespace}`로 출력하고 본문에서 제외한다. 일반적인 파이프 문자는 클러스터로 오인하지 않는다.
- **REQ-PARSE-07 (범위 한정):** 1차 개발은 **Grafana 알람만 지원**하며, SCP 알람은 추후 확장한다.

## 3. 노티 본문 및 Jira 이슈 제목 생성 요구사항
- **REQ-FMT-01 (노티 본문):**
  ```text
  (클러스터가 있을 때만) 클러스터 : {namespace}

  서비스명 : {Target}

  장애현상 : {Detail}

  발생시간 : {YY-MM-DD HH:mm}
  ```
  `Start At`은 24시간제 `YY-MM-DD HH:mm`으로 변환하며, `Duration`은 노티 생성에서 제외한다.
- **REQ-FMT-02 (묶음 노티 본문):** 묶음 대상 알람 블록을 기존 양식 그대로 유지하며 블록 간 빈 줄(엔터)로 구분하여 연결한다.
- **REQ-FMT-03 (Jira 제목 Alert Name 정제):**
  1. 선행 연속 대괄호 제거: 맨 앞의 `[Linux]`, `[Linux][CRITICAL]` 등 `^(?:\[[^\]]*\]\s*)+` 제거.
  2. 후행 심각도 소괄호 제거: 맨 끝의 `(critical)`, `(warning)` 등 `\s*\((?:critical|warning|info|error|fatal|warn|crit)\)\s*$` 제거 (대소문자 무시).
- **REQ-FMT-04 (Jira 제목 출처 태그):**
  - Grafana DB 매칭 시: `[247][GRAFANA]`
  - N3R DB 매칭 시: `[247][N3R]`
  - 양쪽 모두 미매칭 시: 출처 태그를 생략하여 `[247]`만 부여 (빈 괄호나 이중 공백 방지).
  - 양쪽 모두 매칭 시: 담당자 일치 여부와 무관하게 사용자가 화면에서 출처 태그를 직접 선택.
- **REQ-FMT-05 (Jira 제목 생성 공식):**
  - 개별 등록: `[247][출처태그(있을때만)] {Target}, {정제 Alert Name}`
  - 묶음 등록 (동일 장애현상): `[247][출처태그] {첫 Target} 외 {N-1}건, {정제 Alert Name}`
  - 묶음 등록 (다른 장애현상): `[247][출처태그] {첫 Target}, {첫 정제 Alert Name} 외 {N-1}건`

## 4. 다중 알람 처리 및 묶음 등록 규칙
- **REQ-GRP-01:** 사용자는 '개별 등록'과 '묶음 등록' 라디오 버튼을 선택할 수 있다.
- **REQ-GRP-02 (묶음 필수 4대 조건):** 아래 4대 조건을 **모두 만족**하는 알람끼리만 하나의 Jira 이슈로 묶을 수 있다.
  1. 담당자가 동일하다.
  2. 출처 태그(`N3R` 또는 `GRAFANA`)가 동일하다. (미매칭 태그 없음 알람의 묶음은 금지/개별 분리).
  3. `Target`이 같거나 정제된 `Alert Name`이 같다 (`same_target OR same_symptom`).
  4. 사용자가 '묶음 등록'을 선택했다.
- **REQ-GRP-03 (조건 불일치 시 분할):** 위 조건을 하나라도 만족하지 못하는 알람은 강제로 합치지 않고 **독립된 개별 이슈 단위로 자동 분할**한다.

## 5. 워크플로우 및 승인 모드 정책
- **REQ-WF-01 (단일 확인 모드):** '자동 등록' 모드는 삭제하며, **'확인 후 등록' 단일 모드**로 운영한다.
- **REQ-WF-02 (포커스 분리):** 노티 텍스트 편집 영역에 포커스가 있을 때 `Enter`는 줄바꿈으로 동작하며, 승인 버튼에 포커스가 있거나 명시적 단축키(`Ctrl+Enter`)를 누를 때만 등록이 실행된다.
- **REQ-WF-03 (중복 감지):** 당일 동일 알람(`Target | 정제 Alert Name | Start At`)은 메모리 `set`과 로컬 당일 캐시를 통해 0.01초 내 감지하여 경고 팝업을 띄운다. 사용자가 재등록을 명시적으로 확인한 경우에만 진행을 허용한다.
- **REQ-WF-04 (API 상태 머신):** 이슈 등록 상태를 `대기`, `요청중`, `생성성공`, `부분실패`, `생성여부불명(Timeout)`, `최종실패`로 구분한다. 이슈 생성 성공 후 후속 필드 실패 시 **절대 재등록 호출을 하지 않는다**.

---

## 6. 데이터 관리 및 보안 정책
- **REQ-DATA-01:** 외부 DB 없이 로컬 PC에 Grafana DB(`grafana_db.dat`)와 N3R DB(`n3r_db.dat`)를 분리하여 AES 암호화 보관한다.
- **REQ-DATA-02 (Excel Append):** Excel 가져오기 시 기존 로컬 DB에 추가(Append)하며 중복 행을 검증한다.
- **REQ-SEC-01 (계정 및 비밀번호 재설정 - 위험 수용):**
  - 회원가입 시 ID, 비밀번호, 이름을 등록하며 비밀번호는 PBKDF2 단방향 해시로 저장한다.
  - 비밀번호 분실 시 **ID만으로 즉시 새 비밀번호 설정**을 허용한다.
  - **보안 완화 조치:** 비밀번호 재설정 즉시 해당 계정에 등록된 **개인 Jira API 토큰을 완전 삭제(초기화)**하고 기존 로그인 세션을 무효화한다. (본 정책은 계정 탈취 및 DoS 위험이 존재함을 문서화함).
- **REQ-SEC-02 (토큰 보관):** 개인 Jira API 토큰은 Windows Credential Manager 또는 DPAPI를 통해 OS 세션에 안전하게 암호화 보관한다.

---

## 7. 로깅 정책
- **REQ-LOG-01:** 기본 경로는 `C:\noti-log`이며, 사용자가 설정에서 변경할 수 있다.
- **REQ-LOG-02:** 자동 폴더 생성 ON 시 `<경로>\YYYY\MM\YYYY-MM-DD.txt`, OFF 시 `<경로>\YYYY-MM-DD.txt`로 저장하며 이어쓰기(append)한다.
- **REQ-LOG-03 (3단계 Fallback):** 사용자 지정 경로 실패 시 `C:\noti-log` 시도, 이마저도 권한 부족 등으로 실패 시 `%LOCALAPPDATA%\NotiAutomation\logs`로 안전하게 Fallback 적재한다.
- **REQ-LOG-04:** 포맷은 `[YYYY-MM-DD HH:mm:ss] [LEVEL] [User: 이름(ID)] [모듈명] 메시지`를 준수하며, API 토큰 및 비밀번호는 마스킹 처리한다.

## 8. 추가 확정 규칙 및 게이트 (2026-11-01 개정)
- **REQ-WF-05:** 기본 담당자 설정값으로 대체한 미매칭 알람은 1회 안내하고 미리보기에서 수동 수정 허용. 설정된 기본 담당자가 없거나 유효하지 않으면 승인 차단.
- **REQ-WF-06:** 승인된 여러 알람은 각각의 담당자·태그·제목을 독립적으로 확정한 뒤 등록한다. 묶음 선택 시에도 4조건 불충족 건은 별개 이슈로 분할한다.
- **REQ-WF-07:** 동일 날짜 중복 알람은 경고 및 명시적 재등록 확인 후에만 재생성 허용. `UNKNOWN` 및 `PARTIAL_FAILED`는 단순 중복과 다른 상태로 취급하여 별도 수동 대조 게이트 적용.
- **REQ-WF-08:** NoData만 제외하고 나머지 알람 처리 지속. NoData 제외 건수·사유를 알림/로그로 남기고 NoData는 검토 목록이나 Jira 전송 payload에 포함하지 않는다. 파싱 불가 건은 NoData로 간주하지 않는다.
- **REQ-WF-09:** 개별 검토 확인 및 전체 등록 기능 모두 제공. 전체 등록은 각 건의 필수값·충돌·중복·승인 상태를 확인하고 적격 건만 전송하며 미적격 건은 이유 표시.
- **REQ-SEC-03:** ID만으로 새 비밀번호 설정하는 사용자 승인 정책을 유지한다. 그에 따른 타인 계정 탈취/서비스 방해 위험은 **미해결 위험으로 명시**한다. 개인 Jira 토큰 초기화는 그 위험을 제거하지 못한다.
- **REQ-JIRA-01:** 기본 에픽 및 복수 에픽 선택, 기본 참조자와 알람별 참조자를 분리 관리, 사용자별 인증 및 보고자 설정을 지원하도록 설계한다. 실제 필드 매핑은 Jira 종류/스키마 검증 전까지 MOCK 상태로 유지한다.
- **REQ-DATA-03:** Excel 동일 키·동일 내용은 중복으로 스킵하며, 동일 키·다른 담당자/내용은 덮어쓰지 않고 관리자 충돌 검토 대상으로 보낸다.
- **REQ-LOG-05:** 3개 로그 후보 경로 모두 실패해도 Jira 작업 결과를 덮어쓰거나 앱 전체를 종료하지 않는다. 사용자에게 비영구 기록 실패 경고를 표시한다.
